# 导出进入游戏后的八度偏差：检查记录

检查日期：2026-09-09。最初按导出后八度变化排查；随后查看反馈原话与截图，
确认反馈者描述的是游戏内不同乐器的可输入音域，且没有使用本工具做过对照。
本次完成了导出字节检查和用户所选音源的本地渲染；尚未取得同一曲谱的游戏现场录音。

## 已确认的结果

### 用户提供的 v782 PAZ：编辑音域对照

用户随后明确要求本地解包，并将反馈具体化为“工具与游戏的乐器映射范围不一致”。
本次从用户指定归档的 `PAD06445.PAZ` 读取作曲界面的 JavaScript 与 HTML，
只在 Git 忽略的本地诊断目录保存这两个文件；未提取音频，也未增加产品解包入口。
作曲脚本 SHA-256 为
`714f2fa753997ae397a509b0010b2a892d79a2fb551e1513021fdd98b2038a23`。
后续以两个进程扫描该目录全部 8,363 个 PAZ 的文件表，按确切文件名查找
`musiccomposition.js`，仅找到上述一份，没有发现同名脚本覆盖版本。

脚本的静态 `instrument_info.note_number` 表提供起止 MIDI 键号和键名表；
`initNoteNumberList` 按上下限创建琴键，并禁用键名为空的打击乐行。这不是通过音源采样
覆盖范围反推的游戏音域。对照结果：

- 26 个工具乐器、含合成器四档后共 38 个组合，profile 上下限与离散可用键全部一致。
- MIDI 12–127 的旋律音名也一致；游戏将升号写在八度数字之后，工具写在之前，
  仅为排版差别。
- 唯一运行时遗漏是手碟：profile 的 45–88 正确，但旧证据仍为 approximate，
  使 `game_supported_pitches(0x13)` 返回 None。现根据游戏 UI 静态表确认编辑音域，
  编辑器与导出校验使用 45–88（A2–E6），已有越界音符保留供用户修正。
- 修正后 38 个组合的运行时可用键与游戏静态表全部一致。

以上仅适用于这份 v782 归档与当前源码，不能证明反馈者使用的 EXE 或游戏客户端
相同，也不能解决不同乐器的实际声学八度差异。手碟的音频、奏法与游戏 A/B
验证状态不因编辑音域确认而提升。原先对“所有非钢琴乐器范围错误”的猜测，
本次未得到支持。

用户进一步指出截图中的显示范围不同。沿 UI 路径核对后，确实发现显示策略差异：
游戏 `initNoteNumberList` 只生成该乐器起止范围内的琴键，而工具的
`PianoRollCanvas.MIN_PITCH/MAX_PITCH` 为 0/127，`pitch_top_bounds` 使用这个
完整范围。推荐音域只影响初始定位，不能等同于限制滚动边界；
`note_invalid` 独立判断实际合法性。这说明可滚动琴键范围与合法音域是两回事，
配置表一致不能否定截图中的视觉差异。

实际查看反馈截图后，标为“竖笛”的画面顶部为 B6，下方有 C6；而这份资源中
ID 2 的上限为 MIDI 83 / B5。截图没有序列化乐器 ID、MIDI 键号或客户端版本，
因此不能确定是客户端数据差异、乐器对应关系还是音名差异，也不能据此扩大 ID 2
的合法范围或统一移调。钢琴截图还出现高于 C7、低于 C1 的键，反馈文字里的
“最高 C7 / 最低 C1”不是精确端点。下一步需要该竖笛最高键在游戏中保存的
最小曲谱，以解码的乐器 ID 和键号消除歧义。

另已修复普通编辑的音域提示遗漏：此前键边的越界标记只在扒谱候选可见时绘制，
现在手工编辑的空白行也显示该标记，悬停时显示“超出当前游戏音域”。判断复用
导出侧的音域和移调结果；保留完整滚动范围与所有原始音符，不擅自隐藏或改音高。
离屏回归检查同一行在合法移调前后的实际像素和提示变化，确认音符不被改写。
修复后完整回归 1,396 项通过、12 项跳过；语法与仓库检查通过。未重新构建 EXE。

### 导出没有暗中统一升降八度

新增回归测试覆盖 22 个旋律乐器及合成器的四种模式，共 34 种组合。对 profile
每个合法键号构造中性奏法音符，经过正式 `freeze_export_tracks → prepare_export`
再由 `bdo_codec` 解码。所有音高键号、`ntype=0` 和最终乐器/模式 ID 一致。

这是字节和程序行为证据，不是游戏声学验证；也不能替代对用户实际工程中移调、
奏法及模式设置的检查。特别是 `superoct` 和泛音本来就可能改变听感。

测试位于 [`test_bdo_export_roundtrip.py`](../tests/test_bdo_export_roundtrip.py)
的 `test_every_melodic_range_preserves_pitch_and_synth_mode_on_wire`。

### 当前音源下，相同键号已经产生乐器间八度差

只读检查本机保存的设置确认选择的是外部音源包。没有更改设置、提取或复制音源，
没有启动声卡播放。使用现有解码缓存和生产 `_prepare_project`、`_commit_project`、
`_render_locked` 在内存中渲染，限制解码及数值计算为两线程。

固定 MIDI 60、力度 90、中性奏法、1 秒音符、无外加混音效果；渲染约 0.8 秒，
排除前 0.1 秒起音后，以 YIN 估计基频。MIDI 60 按 A4=440 Hz 应为约 261.63 Hz。

| 乐器 | ID | 生产渲染基频估计 | 相对 MIDI 60 |
|---|---|---|---|
| 弗洛凯斯特拉原声吉他 | 0x0A | 262.72 Hz | 接近原音 |
| 弗洛凯斯特拉钢琴 | 0x11 | 524.49 Hz | 约高一个八度 |
| 弗洛凯斯特拉小提琴 | 0x12 | 522.60 Hz | 约高一个八度 |

另外检查这些乐器在 48、56、57、60、61、64、72 的样本基频与正式播放倍率：
吉他接近零偏移，钢琴与小提琴接近 +12 半音，且在已检查的 C4 边界两侧连续。
因此当前样本不能支持“116 条根音校正导致本次边界突跳”的判断。

本机音源的其他初筛：新手竖琴/钢琴/小提琴、高级长笛/竖琴、单簧管在所测
48、60、72 键附近也接近 +12 半音；吉他、电吉他、贝斯、低音提琴、圆号接近
零偏移。新手长笛和 Recorder 的估计不一致，需要逐区复核。初筛使用单一力度、
每个键第一条可用变体和短时基频估计，不能当成完整校音表，更不能推断当前游戏
的全部发声规则。合成器、打击乐及其他奏法不在这项声学初筛内。

## 两个需要保留区分的代码问题

### 历史根音校正是试听行为，不是导出移调

[`effective_sample_root_note`](../src/bdo_music_composer/audio/bdo_instrument_samples.py)
按音色库、键区和原始根音修改试听根音。现有映射命中 116 条：110 条差 12 半音、
1 条差 24、1 条差 36、4 条差 48。相对直接采用原始字段，播放速率会降低
1–4 个八度；原始证据 JSON 与正式 `Note.pitch` 不变。

这是一条重要排查线索，但本次频率测量显示它维持了已检查样本的边界连续性。
不能只看到原始根音与有效根音不同，就删除整张校正表。也不能凭此把游戏发声
认定为原始字段的直接结果；游戏运行时的额外音高处理仍需录音对照。

### 内置通用音源的极端音高截断已修复

旧通用音源把以 A4 为中心的播放倍率限制在 0.125–8，对应 MIDI 33–105。
低于 33 或高于 105 的音符因此不能保持正确频率，例如 MIDI 21 会按 33 播放，
相差一个八度。现已移除该倍率截断，仍将输入键号限定于 MIDI 0–127；不增加
回调分配或 I/O，也不改导出音符。新增测试逐键检查全部 128 个键号，并通过
生产渲染与频谱检查 MIDI 21 / 117 的 27.5 / 7040 Hz，避免只验证内部倍率。
相关通用音源、实时音频及音频生命周期 94 项测试通过。

该分支不用于本次选中的外部包，修复不能冒充已解决游戏中的八度偏差。

### 对“除钢琴、打击乐外全部补偿”的复核

继续分别测量左右声道：高级吉他均约 262.56 Hz；高级钢琴左右声道分别约
524.53 / 524.34 Hz；高级小提琴单声道约 522.81 Hz。钢琴和小提琴在 261 Hz
附近的能量比 523 Hz 附近低约 53–62 dB，不支持“立体声求平均抵消基频”的解释。
小提琴与钢琴属于同一组，吉他/贝斯/圆号等属于另一组。因此现有证据不能支持
按“非钢琴且非打击乐”统一升降八度；需先明确游戏相对工具的偏差方向及乐器。

## 为什么暂时不自动补偿导出

目前可以证明相同键号在选中音源下的发声音高有差异，但还不能区分：

- 音源包的实际基频与游戏自身不同；
- 游戏乐器本就采用不同的记谱/发声音高关系；
- 用户受影响的工程另外带有移调、泛音或合成器模式。

如果现在给钢琴、小提琴等统一减 12，便会改变用户正式谱面，并可能在另一套
音源或游戏处理下造成第二次错误补偿。因此本次没有按声学初筛调整根音表或
导出移调规则；profile 仅补充了前述手碟编辑音域的证据状态。

下一步使用同一组 48、60、72 键、中性奏法和力度 90，在游戏里逐乐器录音，
再与这里的生产渲染对照。应同时保留实际导出的 BDO 曲谱用于解码，游戏截图的
C3/C4 标签不能替代 MIDI 键号与基频。录音与曲谱是私有验证资料，不进入 Git。
